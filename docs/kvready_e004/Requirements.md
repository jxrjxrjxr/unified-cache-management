# E004：需求与认知对齐

**E004 要交付一套以预取为主、加载与重算配合的可运行方案，并回答：在 PD 分离场景中，外部前缀缓存如何更早到达消费端，经存储交接 KV 是否能够减少互联争用、改善服务性能？** KV 缓存是注意力计算中可复用的键和值；PD 分离把提示词处理（Prefill，P）与逐 token（模型处理的基本单元）生成（Decode，D）放到不同执行实例。

正文依次说明交付目标、技术问题、测试要求和协作流程；文末附录保存历史依据、版本状态、待确认事项与用户原文。

## 1. 交付目标

交付分为方案、代码和实验结论三部分，三者围绕同一条预取主线展开。

**方案说明为什么值得做。** 从已有论文和代码出发，选出一个清楚的新增决策或机制，解释信号从哪里来、提前搬什么、何时消费、预计节省哪段等待，以及新增开销。预估收益采用可核对的成本估算，并在实施前给出适合验证该收益的常规负载。

**代码让方案可以直接运行。** 实现和专用测试进入 UCM（统一 KV 缓存管理系统）个人仓库的 `kvready/e004` 分支，与用户所指个人 UCM 仓库的 `kvready/e003` 保持同源。AI 完成开发、蓝区可运行的检查、提交及 push，并提供黄区取得指定提交和运行测试的简明步骤。蓝区承担开发与检查；黄区承担实际部署验证。

代码在已确认方案内采用最小改动，优先复用现有接口与执行能力；新增模块只承担预取协调、真实完成和专用验证所需职责。

**实验结论服务于主管交付。** 最终报告连贯回答：新增预取机制带来了什么变化；加载和重算怎样配合；KV 交接改走存储需要哪些条件；互联是否位于性能关键路径；哪些负载值得继续投入。配套一个或少数几个演示用例、可复现实验结果和适用条件。

## 2. 技术问题

技术工作分为预取决策、恢复决策和传输路径三个相互配合的部分；预取决策承担主要创新和效果验证。

### 2.1 提前准备消费端需要的 KV

Layerwise 指按模型层组织加载或传输，使搬运与计算重叠。E004 在这一执行条件下研究 PD 场景中 KV transfer（KV 搬运）的提前准备策略。创新说明必须指出：相对于现有逐层执行，增加了什么可用信息、提前了哪个时间点、改变了什么搬运或资源分配决策。

例如，共享长前缀的请求到达 P 后，D 将来会消费这段前缀。若路由和缓存身份已经确定，可以研究在 P 处理剩余输入期间，为 D 提前准备外部已有的前缀 KV。这是用于确认需求含义的候选例子；具体信号、位置和提交时机由方案阶段选定。

UCM 已有的下一层提前加载、既有 PD 逐层提前发送，以及经共享存储交接 KV，作为基础能力纳入对照。新增策略的效果用相同执行能力、相同可用信息与资源预算下的比较衡量。研究结论需要明确相对已有论文和代码的具体增量。

### 2.2 让加载和重算配合预取

加载是把已有合法 KV 搬到执行端；重算是根据输入重新计算 KV。两者围绕“怎样让请求更快获得可用 KV”配合预取：请求需要继续执行时，根据已经完成的预取与剩余成本选择恢复方式。

设计采用实现规模可控、能保持模型输出正确的动作集合。实际采用的加载范围、重算范围和完成条件应在方案中写清楚，并在测试中观测。比较覆盖常规的收益区间，使预取贡献与加载／重算选择贡献能够分别解释。

### 2.3 评估存储路径与互联争用

主管在 2026-09-17 提出的方向是：Prefix Cache（复用相同输入前缀的 KV）与 PD 分离结合；外部前缀命中后，PD 之间通过存储路径交接 KV，把其所称的“控制超平面”资源留给 MoE（混合专家模型）的专家通信。

可行性分析需要画清逻辑数据路径，并对应实际物理资源：已有前缀在哪里、P 和 D 各自读什么、P 新产生的 KV 怎样交给 D、哪些传输使用同一互联。两种路径比较都覆盖完整请求的 KV 依赖和准备成本。

小规模演示要观测 KV 就绪、P 计算完成、D 恢复执行与客户端首 token 返回之间的关系，并结合链路负载变化判断瓶颈。若使用通信负载模拟 MoE 争用，报告应明确模拟对象与真实模型验证之间的关系。

## 3. 测试要求

测试围绕主流程有效性、收益归因和执行成本组织，优先把问题在蓝区暴露出来，再交付固定的黄区验证批次。

**主流程有效性。** 测试使用正常输入、合理输出长度和足够统计样本，并给卡数、内存、并发、请求量与运行时长设定上限。检查真实返回是否满足指标计算条件，每个请求恰好形成一条记录；异常保留原因并结束对应比较。缓存准备和清理采用可验证的完成条件。

**收益归因。** 从共享长前缀、多轮会话或检索增强问答等常见负载选取少量代表场景，各方案重放相同请求、到达过程和缓存起点。预取对照保留已有逐层能力；传输路径对照保持相同策略；加载／重算对照解释剩余恢复成本。完整核算准备开销、传输字节与请求等待，结合 TTFT（从请求发出到首 token 返回的时长）和生成阶段表现评价收益。

**执行成本。** 测试集成在 UCM 的 `test/` 下，用一个或数个职责清楚的文件承载。策略检查、真实服务验证、结果汇总各有专一职责。黄区一次运行完成一个预先规定的批次，输出少量可手抄的摘要，详细结果留在黄区。完成约定批次后收口；出现主流程阻断时，AI 在蓝区集中分析和修复，再交付下一批。

测试范围集中在能跑通、能验证、具有生产代表性的主流程。必要的正确性和资源保护检查随实现完成；边界穷举、压力极限和持续追加测试不列入 E004 主线。收益是否可观由真实比较确认；实现前先依据历史数据和成本关系选择有收益空间的负载。

## 4. 协作流程

协作依次经过认知对齐、AI 端到端开发、黄区反馈和报告交付四个阶段。

1. **认知对齐。** AI 根据用户 Prompt、E001–E003 和既有研究形成这份需求解释；用户确认目标及必要环境信息。
2. **方案与开发。** 对齐后，AI 查证所需论文和代码，完成预取、加载、重算及存储路径的完整方案并落文件，交由用户再次确认；方案确认后再实现、检查、提交和 push。常规实现选择由 AI 完成。
3. **黄区反馈。** AI 给出取得指定提交、启动服务和运行专用测试的步骤；用户实际执行并手抄少量摘要。每批标明命令数量、预计操作量、反馈字段和结束位置；主流程问题集中回蓝区处理。
4. **报告交付。** AI 将代码行为、实测结果、收益归因和适用条件汇成主管可读的可行性报告，持续交互至形成可交付结果。

E004 的“无干预”覆盖认知对齐后的蓝区开发过程，黄区访问由用户承担。日常代码选择和必要修复按已确认需求自主推进；改变交付目标、引入新依赖或遇到确实缺少的环境事实时再沟通。AI 按要求充分迭代检查，确认主线达到交付条件后再交给用户去黄区拉取验证。

所有面向用户的会话和文件遵守附录中的五条风格准则。交付前依次自检标题树、认知顺序、表达基调、术语锚定和认知负担；由另一名 AI 进行交叉评审，按“准则编号＋判定＋原文引用＋最小修改建议”记录，判定采用达标、基本达标、需要修改。

## 一、信息分级：先分清三层

## 二、输出风格约束

### 约束一 · 标题树：同级同质、父子显式、可 BFS 遍历

- 标题构成一棵显式的树：父标题界定范围，子标题在父范围内并列展开。
- 同一父节点下的兄弟标题属于同一抽象层级、同一分类维度。
- 每个父标题下用一句话说明子标题之间的关系（导航句），读者由此知道这一层怎么展开。
- 只读某一层的标题，就能得到该层的完整画面；细节留给下一层。第一遍阅读是一次广度遍历。
- 层级数量按内容需要决定，能用一个层级讲清的，不制造下一个层级。

### 约束二 · 认知顺序：动机在前，元信息在后

- 文档要回答的问题出现在开头，读者由此知道每一节为何存在。
- 边界、版本、环境、验证状态与免责说明集中放在文末固定位置；正文段落专注正面内容。
- 正文中确有必要的限定，用一句正面陈述给出范围，随该处内容一并说完，不另起一段。
- 元信息层不参与认知推进，它的位置在文末或文末附录，不在开头与中段。

### 约束三 · 表达基调：以肯定式陈述承载结论

- "这不代表……""不能证明……"式的对冲集中到元信息层。
- 需要指出某条路径不成立时，说出成立的范围、替代解释或成立条件。
- 例外只有一类：用户明确要求纠错、风险提示或安全边界说明时，直接指出问题本身。

### 约束四 · 术语锚定：首用即定义

- 专业名词、代号、缩写第一次出现时给出最小定义或指向。
- 会话相对指代（"本轮""本次""当前""本机"）落到绝对锚点：日期、事件、文件。
- 后续引用已定义的术语时直接使用，不再重复解释。

### 约束五 · 认知负担：解释过程保持连续

- 表格、多级标题、列表都消耗层级切换精力，按需使用。
- 表格用于查表与横向对照，归入支撑层或元信息层；解释过程用连续文字加少量要点。
- 需要读者先记住一组符号才能理解结论时，先给一次真实样例或输出结构，再给字段表。
- 示例紧跟它所说明的概念。
- 同级条目同质：一条要点承载一件事；需要声明"这两处不同"时，说明它应当拆分。

## 三、非量化评估准则

判定只给结论，不折算分数，依据是原文引用。

### 准则一 · 标题树

- 检查问题：只读某一层的标题，能否得到该层的完整画面？兄弟标题是否同质？每个父标题下是否有导航句？
- 反例特征：标题之间的关系要靠正文才能推断；同级标题分属不同层级；标题引用前文未出现的概念。
- 修改方向：补导航句、把不同质的标题拆到不同父节点、把非标题层级的内容降为正文。

### 准则二 · 认知顺序

- 检查问题：文档要回答的问题是否出现在开头？元信息是否集中在文末？
- 反例特征：版本、环境、未验证声明出现在开头或中段；动机晚于第一节。
- 修改方向：把元信息整段移到文末附录，开头只留问题与主线。

### 准则三 · 表达基调

- 检查问题：结论是否由肯定句承载？是否存在对读者认知的直接否定，或成串的对冲？
- 反例特征：核心判断写成"X 不足以证明 Y"；正文散布"不能/尚未/不代表"。
- 修改方向：改写为正面判据与适用范围，对冲集中到元信息层。

### 准则四 · 术语锚定

- 检查问题：术语首用处是否给出定义或指向？是否存在只在此次对话中有意义的指代？
- 反例特征：专名先于解释出现；"本轮""本机"承载关键指代。
- 修改方向：首用处补最小定义；相对指代改为日期或文件锚点。

### 准则五 · 认知负担

- 检查问题：解释过程中是否需要先背一组符号？表格是否出现在理解之前？
- 反例特征：字段表先于任何样例；讲解中插入对照表；一条要点自述包含两件事。
- 修改方向：先给样例或输出结构，再给字段表；表格移入附录；拆分不同质的条目。
